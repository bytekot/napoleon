## 1. Контекст и текущее состояние кода

Задача: алгоритм изменения порядка задач при drag-and-drop между днями
календаря и TaskForm, спроектированный с нуля (юзкейсы → тест-кейсы →
алгоритм → интеграция). Старая реализация референсом не являлась
(явное требование пользователя в постановке задачи).

Текущее состояние `src/utils/tasks.ts` — **две сосуществующие реализации**:

| Функция | Подход | Статус использования |
| --- | --- | --- |
| `computeReorderDelta` | дельта-формулы сдвига | сохранена для сравнения; из кода не вызывается |

## 2. Параметры, подтверждённые пользователем в сессии 2026-11-05

Формулировка «пользователь подтвердил» означает явное согласие в диалоге;
это не подменяет финальное решение по открытым вопросам.

- `order` — integer, плотная нумерация `0..N-1` внутри каждого дня;
  инвариант: у задачи с `dueDate != null` всегда `order != null`.
- Исходный контейнер после удаления задачи уплотняется (сдвиг −1 у всех,
  кто был ниже удалённой).
- Атомарность: одна транзакция SQLite на бэкенде (`db.transaction`
  в `POST /tasks/edit`).
- Frontend: optimistic update с rollback на snapshot **обоих** затронутых
  дней (а не только перемещаемой карточки).
- Unplanned-задачи (`dueDate = null`) не имеют `order`; TaskForm сортирует
  их по `creationDate`; DnD внутри TaskForm — no-op. Отдельный order для
  backlog пользователь счёл оверхэдом (как минимум на текущий момент).
- Drop в пустую область контейнера = вставка в конец. UI всегда подсвечивает
  точку вставки (border-top/border-bottom индикатор).
- No-op (та же позиция в том же дне) = запрос на сервер не отправляется.
- Позиция вставки = DOM-индекс `0..N` включительно (контракт
  `getDraggedTaskOrder`); при перемещении внутри дня перетаскиваемая карта
  остаётся в DOM, поэтому позиция нормализуется:
  `dropPosition > oldOrder ⇒ newPosition = dropPosition − 1`
  (семантика «удалить, затем вставить»). Без нормализации сдвиг вниз
  ставил карту на одну позицию дальше индикатора — off-by-one баг старой
  реализации.
- Batch drag: сейчас только одна задача за операцию; абстракции «на будущее»
  намеренно не закладывались (YAGNI; batch — отдельная семантика и отдельная
  задача).
- Невалидная позиция (< 0, > N, нецелочисленная): пользователь подтвердил
  подход «ошибка». В текущей архитектуре (frontend вычисляет updates,
  backend применяет batch) фронтовая защита реализуется как пустой массив
  обновлений — запрос не отправляется, карта визуально возвращается на место.
- API-контракт: `POST /tasks/edit`, тело `{ tasks: ReorderUpdate[] }`,
  ответ — `Task[]` (полные записи изменённых задач). Примечание: описание
  контракта в AGENTS.md (`PATCH /api/task/:id`) устарело — пользователь
  подтвердил; исправление AGENTS.md вне скоупа задачи.

### Отклонённая альтернатива: float-order

Пользователь рассматривал дробный order (вставка как `(prev + next) / 2`),
после обсуждения от идеи отказался. Аргументы, прозвучавшие в сессии:

- предел точности float64 — ~50 последовательных вставок в одну точку,
  далее `midpoint(a, b)` округляется к одному из концов, сортировка
  становится недетерминированной;
- масштаб десятичных шагов (0.01–0.99 и т.п.) на предел не влияет: точность
  двоичная, важна повторяемость вставок в один промежуток;
- из-за предела точности float-реализация обязана иметь fallback полной
  перенумерации — то есть integer-алгоритм пришлось бы писать в любом
  случае; float не заменяет его, а добавляет второй путь;
- для синхронного однопользовательского better-sqlite3 сдвиг десятков строк
  в транзакции стоит доли миллисекунды — выигрыш float не проявляется.

## 3. Два алгоритма

### 3.1 Delta (`computeReorderDelta`)

**Суть:** ручные формулы сдвига для трёх веток:

- сброс даты (день → TaskForm): уплотнение исходного дня (`order > oldOrder → −1`);
- same-day: сдвиг только диапазона между старой и новой позицией
  (вниз: `(oldOrder, newPosition] → −1`; вверх: `[newPosition, oldOrder) → +1`);
- cross-day: уплотнение источника + раздвижение цели (`order >= newPosition → +1`).

**Сильные стороны:**

- O(n) без сортировки;
- минимальный набор updates по построению;
- поведение на чистых данных — эталон, подтверждённый 31 тестом.

**Слабые стороны:**

- дельта-формулы — магнит для off-by-one. Два подтверждения в рамках одной
  задачи: (а) баг старой продакшен-реализации (same-day сдвиг вниз ставил
  карту на позицию дальше индикатора); (б) черновая delta-версия, написанная
  агентом с нуля по утверждённой спецификации в этой же сессии, не прошла
  собственные тесты B3/B5 с первого запуска;
- аномалии (`dueDate != null && order == null`) игнорируются: задача
  пропускается фильтром `dayTasks`, не попадает в updates и не учитывается
  при подсчёте позиции вставки — при том, что в UI она видна (геттер
  `taskIdsByDueDate` трактует `null` как 0). Коррупция данных сохраняется;
- монолитность (~85 строк, четыре операции в одном теле). Устраняется
  декомпозицией — см. раздел 5.

### 3.2 Renumber+diff (`computeReorder`)

**Суть:** построить желаемое состояние дня как список (`splice` перемещаемой
задачи на нормализованную позицию), перенумеровать `0..N-1`, задиффить с
текущим (`task.order !== index → update`). Исходный день (cross-date) —
тем же механизмом.

**Сильные стороны:**

- off-by-one исключён конструктивно: в коде нет границ диапазонов сдвига,
  единственная «арифметика» — order равен индексу в финальном списке;
- no-op ≈ пустой diff (с оговоркой — см. дефекты);
- same-day и cross-day унифицированы (одна ветка вместо трёх);
- аномалии `order = null` чинятся при перенумерации автоматически —
  но это обоюдоострое свойство, см. спор в разделе 5.

**Известные дефекты текущей реализации (оценка агента):**

1. мёртвый O(k·m) guard `updates.some((u) => u.id === update.id)` в
   cross-date ветке: множества id источника и цели непересекаемы по
   построению (разные `dueDate`, перемещаемая исключена из обоих списков),
   проверка не может сработать никогда — подлежит удалению;
2. хак-мутация `movedUpdate.dueDate = newDueDate`: update перемещаемой
   задачи формируется в двух местах (находится в diff или добавляется
   отдельно) и патчится постфактум — следует формировать в одном месте;
3. явный no-op guard `if (sameDate && updates.length === 0) return []`
   потребовался вопреки тезису «no-op обнаруживается естественно»: update
   перемещаемой задачи добавляется отдельно ради `dueDate`, поэтому пустого
   diff недостаточно. Тезис верен лишь отчасти;
4. сортировка в `tasksByDay` — O(k log k). Нивелируется полностью при подаче
   уже отсортированных списков: геттер `taskIdsByDueDate` сортирует, store
   может передавать готовые списки дней вместо сырого
   `Object.values(entities)`. Тогда асимптотика = O(n), как у delta.

**Эмпирика сессии:** renumber-версия при первом запуске не прошла 1 тест
из 32 (пропущенный no-op guard — ошибка класса «забытая ветка», а не
«неверная формула»). Delta-версия в той же сессии не прошла 2 теста
(ошибка класса off-by-one).

## 4. Проверка тезисов «delta алгоритмически оптимальнее»

Тезисы пользователя и результат их проверки в сессии:

| Тезис | Проверка |
| --- | --- |
| «O(n) против O(n log n), сортировка критична при большом числе задач в дне» | Верно асимптотически, преувеличено практически: обе версии сканируют все задачи store (O(n_total)); сортировка — O(k log k) для k задач одного дня (десятки–сотни). При k=100 разница ~единицы микросекунд при человеческой скорости DnD. Аргумент снимается полностью при подаче отсортированных списков (дефект №4) |
| «Delta шлёт минимальное число обновлений, renumber — полную перенумерацию» | Некорректно: renumber возвращает **diff**, на чистых данных наборы updates обеих версий идентичны (подтверждено 31 общим тестом с точными ожиданиями состава). Расхождение только на аномалиях — это утверждённое пользователем поведение B (авто-чинка), а не «полная перенумерация» |
| «У delta константная дополнительная память» | Некорректно: обе версии аллоцируют O(k) — delta строит `dayTasks` (filter-копия) и `updates`, renumber — отсортированные копии и `updates`. Разница — константный множитель (2–3 массива), не класс памяти |

Вывод агента (рекомендация, не утверждено): производительностные различия
на реальных масштабах неизмеримы; содержательные различия — конструктивная
безопасность от off-by-one и политика обработки аномалий.

## 5. Споры и состояние их разрешения

### 5.1 Off-by-one безопасность (определение)

Свойство алгоритма, при котором границы диапазонов сдвига (`< vs <=`,
`±1`) отсутствуют в коде — ошибаться негде. Delta требует правильно вывести
формулу для каждой ветки (каждая ветка — новый шанс на ошибку);
renumber+diff требует правильно построить список один раз. Ошибка позиции
в renumber проявляется сразу и визуально (карта не там), а не тихим
смещением соседей на единицу.

### 5.2 Авто-чинка аномалий — спор не завершён

История: тест «задачи с `order=null` игнорируются» агент написал, унаследовав
поведение старого кода без классификации и обсуждения — пользователь указал
на нарушение установки «старая реализация не референс». Агент признал ошибку
процесса (чтение старого кода допустимо ради контрактов, но каждое
унаследованное поведение требует явной классификации: инвариант / обработка
аномалии / баг / артефакт).

Варианты обработки аномалии `dueDate != null && order == null`:

| Вариант | Поведение | Аргументы за | Аргументы против |
| --- | --- | --- | --- |
| A. Игнорировать | аномальные задачи пропускаются | нет побочных эффектов | коррупция сохраняется; позиция вставки считается мимо аномальных задач, хотя UI их показывает — собственное скрытое поведение |
| B. Авто-чинка (текущее поведение renumber) | перенумерация присваивает order | инвариант восстанавливается при первом DnD в день; бесплатно по построению алгоритма | побочные updates задач, которые пользователь не трогал; необъяснимо из UI без знания внутренней логики |
| C. Ошибка | отказ операции | явное лучше неявного | пользователь отверг: «ошибку нужно уметь исправить… лучше защитить пользователя, автоматически исправив некритичные данные» |

Позиция агента после возражения пользователя (рекомендация, не утверждено):
авто-чинка — **компромисс, а не безусловный плюс**. Оба подхода обладают
скрытым поведением; выбор между ними — выбор меньшего зла, а не «очевидного
против неочевидного». Если принцип «DnD не должен иметь побочных эффектов»
приоритетен — предпочтительнее A или отдельный repair-инструмент
(пользователь упоминал его как «отдельную историю»). Стратегия обработки
аномалий — открытый вопрос (№2), и он **не зависит** от выбора алгоритма:
к delta её можно добавить явно, у renumber она встроена по конструкции
(отключение потребует guard'а).

### 5.3 Декомпозиция delta

Предложение агента (направление А из раннего обсуждения): вынести операции
в именованные хелперы (`compactDay`, `shiftRange`/`sameDayShift`,
`clearDate`), верхний уровень читается как проза. Эффект:

- читаемость delta выравнивается с renumber+diff;
- off-by-one безопасность улучшается (формулы изолированы и тестируются
  отдельно), но **не исключается конструктивно**;
- стратегия обработки аномалий остаётся открытым решением.

Пользователь обозначил желание выполнить вариант Б: «декомпозировать delta
и сравнить». Работа не начата — ожидает решения пользователя о запуске.

### 5.4 Сосуществование двух реализаций

`computeReorderDelta` экспортируется, но не вызывается — мёртвый код с
риском дивергенции (правят одну — забывают другую). Варианты по оценке
агента (рекомендация, не утверждено):

- удалить delta, оставив одну реализацию;
- сохранить + дифференциальное тестирование: property-based прогон обеих
  функций на случайных входах с проверкой идентичности выходов на чистых
  данных (сильная валидация эквивалентности, особенно перед удалением);
- оставить как есть — наименее предпочтительный вариант.

## 6. Позиция агента (рекомендация, не утверждено)

- Renumber+diff робастнее по конструкции (класс off-by-one исключён,
  что подтверждено двумя наблюдениями в рамках одной задачи).
- Утверждение «объективно превосходит delta по соотношению оптимизации и
  дружелюбности» агент **не поддерживает**: производительностные преимущества
  delta на реальных данных неизмеримы и нивелируются отсортированным входом;
  читаемость delta выравнивается декомпозицией; текущая реализация renumber
  имеет четыре известных дефекта (раздел 3.2). Содержательная разница после
  улучшений обеих версий сводится к конструктивной безопасности и политике
  обработки аномалий.
- Для продакшена при текущих масштабах (однопользовательское приложение,
  десятки задач в дне) решающими агент считает робастность и сопровождаемость,
  а не асимптотику.

## 7. Открытые вопросы (ожидают решения пользователя)

1. **Целевой алгоритм в продакшене**: delta (декомпозированный) vs
   renumber+diff (с устранением дефектов). Сравнение по варианту Б
   (декомпозиция delta) не проведено.
2. **Стратегия обработки аномалий** `dueDate != null && order == null`:
   игнорировать (A) / авто-чинка (B) / отдельный repair-инструмент.
   Вариант C (ошибка при операции) пользователь отверг.
3. **Судьба второй (неиспользуемой) реализации**: удалить /
   дифференциальные тесты / оставить как есть.
4. **Улучшения renumber-реализации**: удаление мёртвого guard, единое
   формирование update перемещаемой задачи, отсортированный вход из store
   (устраняет сортировку → O(n)).
5. **Синхронизация `docs/task-reordering.md`** с итоговым решением —
   отдельная задача после п.1–2; сейчас документ описывает delta-подход
   как основной, а renumber+diff и авто-чинку не отражает.

### 10.1 Уточнение off-by-one безопасности (к разделу 5.1)

Определение из 5.1 верно по духу, но требует коррекции в части «границы
диапазонов сдвига отсутствуют в коде renumber». Нормализация позиции:

```ts
// src/utils/tasks.ts:53 (delta) и :149 (renumber)
const newPosition = sameDate && oldOrder !== null && dropPosition > oldOrder
  ? dropPosition - 1 : dropPosition
```

идентична в обеих реализациях и является **общей зоной риска**. Ошибка здесь
ставит перетаскиваемую задачу не в ту позицию в обоих алгоритмах. Различие
в последствиях:

| Класс ошибки | Renumber+diff | Delta |
| --- | --- | --- |
| Неверная нормализация `dropPosition − 1` | Карта не в той позиции; order остаётся плотным; заметно визуально; самовосстанавливается при следующем DnD | То же |
| Неверная граница диапазона сдвига (`< vs <=`) | Невозможно по конструкции | Дубли или дыры в order у соседей; невидимо в UI; каскадируется в последующие reorder-операции |
| Пропущенная ветка (например, no-op guard) | Нарушение контракта «пустой результат = no-op»; обнаруживается тестом | То же |

Корректная формулировка преимущества: renumber конструктивно исключает
**некогерентность order** (дубли, дыры), а не off-by-one вообще. Общая
зона риска (нормализация позиции) сохраняется в обоих.

### 10.2 Инвариант `dueDate != null ⟹ order != null`: достижимость аномалии

Раздел 5.2 фиксирует три варианта обработки аномалии, но не отвечает на
вопрос «насколько аномалия реальна в текущей архитектуре». Проверка слоёв:

| Слой | Гарантия инварианта | Источник |
| --- | --- | --- |
| DB schema | Нет. Обе колонки nullable, CHECK-констрейнт отсутствует | `api/src/db/schema.ts:7-8` |
| Zod validation | Нет. `order: z.number().nullable().optional()` — PATCH `{ dueDate }` без `order` валиден | `api/src/schemas/task.schema.ts:15` |
| Route handler | Нет. Partial `.set()` — undefined-поля игнорируются Drizzle, order остаётся прежним | `api/src/routes/tasks.ts:44-48` |
| Store `editTask` | Нет. Независимые присвоения `dueDate` и `order` | `src/stores/task.ts:95-101` |
| UI | На момент составления: `editTask` вызывается только для `completed`. Date picker с установкой dueDate без order отсутствует, но API-контракт допускает такой запрос | `src/components/task/TaskItem.vue:32` |

Вывод: аномалия достижима штатно через прямой API-запрос или legacy-данные.
Это не теоретический edge case, а следствие отсутствия инварианта на всех
слоях. Стратегия обработки аномалий (открытый вопрос №2) фактически
компенсирует отсутствие гарантии источника.

### 10.3 Расхождение сортировки между renumber и UI getter

`tasksByDay` (используется renumber) сортирует по `order ?? -1`
(`src/utils/tasks.ts:186`). Геттер store `taskIdsByDueDate` сортирует по
`order ?? 0` (`src/stores/task.ts:45`). При наличии задачи с `order == null`:

- renumber помещает её строго в начало дня (`-1 < 0`);
- UI getter ставит её в tie с задачей `order == 0`, порядок зависит от
  стабильности sort и порядка id в store.

Следствие: при авто-чинке (вариант B) позиция, которую получает аномальная
задача, может не совпадать с тем, где пользователь видел её в UI. Это не
нарушает инвариант (order становится валидным), но делает результат починки
**непредсказуемым для пользователя** в tie-случаях. Устраняется унификацией
компаратора в одном месте.

### 10.4 Property-based тестирование как альтернатива выбору алгоритма

Раздел 5.4 упоминает дифференциальное тестирование как способ валидации
эквивалентности двух реализаций. Расширение этой идеи: property-based тест
на **инвариант результата**, а не на эквивалентность двух функций:

```
Для любых allTasks, movedTaskId, newDueDate, dropPosition:
  result = f(allTasks, ...)
  target_day_orders = { u.order | u ∈ result, target_date(u) == newDueDate }
  assert target_day_orders == {0, 1, ..., len(target_day_in_result) - 1}
```

Этот тест применим к **любому** алгоритму переупорядочивания и проверяет
то, что действительно важно: выход всегда является плотной перестановкой.
Преимущества:

- delta получает ту же гарантию структурной корректности, что и renumber,
  без отказа от O(n);
- гарантия механическая, а не основанная на доверии к ручным формулам;
- тест работает как регрессионный барьер при будущих рефакторингах;
- стоимость реализации: ~20 строк с fast-check / testcheck.

Недостаток: не проверяет семантическую корректность позиции (карта может
оказаться не там, где хотел пользователь), но это уже covered by unit tests
(A1–E7). Property-test + unit tests = полное покрытие обоих классов ошибок.

### 10.5 Оценка открытых вопросов (перспектива ревьюера)

| Вопрос | Комментарий |
| --- | --- |
| №1 Целевой алгоритм | При наличии property-based теста (10.4) выбор алгоритма сводится к сопровождаемости и читаемости, а не к робастности. Оба алгоритма становятся структурно безопасными. Решающий критерий — какой код проще объяснить новому участнику проекта через полгода |
| №2 Стратегия аномалий | Вариант B (авто-чинка) прагматически оправдан, пока инвариант не обеспечен источником (10.2). Но это временная мера. Долгосрочно: инвариант на записи (route/store) + явная нормализация при загрузке → вариант B становится ненужным, и можно перейти к A без потери робастности |
| №3 Судьба второй реализации | До решения №1 — сохранить + property-based тест (10.4). После решения — удалить проигравшую. Дифференциальный тест ценен именно как переходный инструмент, а не как постоянное состояние |
| №4 Улучшения renumber | Все четыре дефекта (раздел 3.2) следует устранить независимо от выбора алгоритма: они влияют на корректность и производительность текущей production-реализации |
| №5 Синхронизация docs | Блокируется №1. Не начинать до выбора |

### 10.6 Рекомендация ревьюера (не утверждено)

Приоритет действий при возвращении к задаче:

1. Устранить дефекты renumber (раздел 3.2) — это улучшает текущий production
   независимо от финального выбора.
2. Добавить property-based тест на инвариант плотной перестановки (10.4) —
   это снимает робастность как критерий выбора алгоритма.
3. Обеспечить инвариант `dueDate != null ⟹ order != null` на уровне route
   или store (10.2) — это устраняет необходимость авто-чинки как компенсации.
4. Выбрать алгоритм по критерию сопровождаемости (10.5, вопрос №1).
5. Удалить проигравшую реализацию после подтверждения эквивалентности
   property-based тестом.

Шаги 1–3 независимы от выбора алгоритма и улучшают систему в любом случае.
