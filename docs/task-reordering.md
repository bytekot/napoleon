# Переупорядочивание задач при drag-and-drop

Документ фиксирует соглашения, алгоритм и защиту инвариантов перемещения задач
между днями календаря и TaskForm. Реализация: `src/utils/task/reordering.ts`
(`computeReorder`), DOM-утилита: `src/utils/task/dom.ts` (`getDraggedTaskOrder`),
интеграция: `src/stores/task.ts` (`reorderTask`), тесты:
`src/utils/task/__tests__/reordering.spec.ts`, `src/stores/__tests__/task.spec.ts`.

## Соглашения (утверждены)

| Параметр | Решение |
| --- | --- |
| Тип `order` | Integer, плотная нумерация `0..N-1` внутри каждого дня |
| Инвариант | У задачи с `dueDate != null` всегда `order != null`; «дырок» в нумерации дня нет |
| Unplanned-задачи (`dueDate = null`) | Не имеют `order` (`null`). TaskForm сортирует их по `creationDate`, DnD внутри TaskForm — no-op |
| Исходный контейнер | После удаления задачи уплотняется (сдвиг −1 у всех, кто был ниже) |
| Позиция вставки | DOM-индекс `0..N` (см. «Контракт позиции») |
| Drop в пустую область | Вставка в конец списка |
| No-op | Запрос на сервер не отправляется |
| Batch drag | Не поддерживается (одна задача за операцию); намеренно не закладывался |
| Атомарность | Одна транзакция SQLite на бэкенде (`PATCH /tasks`) |
| Frontend | Optimistic update с rollback на snapshot обоих затронутых дней |
| Валидация позиции | Невалидная позиция → пустой массив обновлений, запрос не отправляется |

Отклонённая альтернатива: дробный `order` (float, вставка как `(prev+next)/2`).
Причины: предел точности float64 (~50 вставок в одну точку) требует fallback
полной перенумерации — то есть integer-алгоритм пришлось бы писать всё равно;
недетерминированная сортировка при коллизиях; масштаб чисел (0.01–0.99 и т.п.)
не влияет на предел точности. Для синхронного однопользовательского
better-sqlite3 сдвиг десятков строк в транзакции стоит доли миллисекунды.

## Контракт позиции

`getDraggedTaskOrder(element, clientY)` возвращает DOM-индекс точки вставки
в целевом `[data-task-list]`:

- наведение на верхнюю половину карты с DOM-индексом `k` → `k`;
- наведение на нижнюю половину карты с DOM-индексом `k` → `k + 1`;
- drop в пустую область контейнера → `childElementCount` (вставка в конец).

Важный нюанс: при перемещении **внутри того же дня** перетаскиваемая карта
остаётся в DOM и входит в этот индекс. Поэтому `computeReorder` нормализует
позицию к семантике «удалить, затем вставить»:

```
newPosition = (sameDate && dropPosition > oldOrder) ? dropPosition - 1 : dropPosition
```

Пример: день `[X, Y, Z, W]`, X перетаскивается под Z (DOM-позиция 3).
Без нормализации X встался бы на индекс 3 (после W); с нормализацией —
`newPosition = 2`, итог `[Y, Z, X, W]`, что соответствует визуальному
индикатору (border-bottom у Z).

Для cross-day перемещений перетаскиваемой карты в целевом DOM нет, позиция
уже соответствует семантике «вставить в список без перемещаемой задачи».

Валидные диапазоны: cross-day — `0..M` (M = число задач в целевом дне);
same-day — `0..M-1` после нормализации. Выход за диапазон, нецелочисленная
или отрицательная позиция → `computeReorder` возвращает `[]` (запрос не
отправляется, карта визуально возвращается на место).

## Алгоритм `computeReorder(allTasks, movedTaskId, newDueDate, dropPosition)`

Алгоритм: renumber+diff. Строит желаемое состояние дня как упорядоченный
список, перенумеровывает `0..N-1`, диффит с текущим состоянием. Возвращает
минимальный набор `ReorderUpdate[]` — только фактически изменённые задачи.
Пустой массив = no-op или невалидные данные.

### Почему renumber+diff

- Конструктивная безопасность от нарушения плотности нумерации: order равен
  индексу в финальном списке, дубли и дыры невозможны по построению
- Единая ветка для same-day и cross-day (нет отдельных формул сдвига)
- Нормализация позиции — единственная зона риска off-by-one (общая с любым
  алгоритмом); последствия ошибки ограничены позицией одной карты, а не
  коррупцией нумерации соседей

### Шаги алгоритма

1. **Сброс даты** (`newDueDate = null`): если задача уже unplanned → `[]`.
   Иначе: убрать задачу из исходного дня, перенумеровать остаток, вернуть
   updates + `{ dueDate: null, order: null }` для перемещаемой.

2. **Нормализация позиции**: при same-day и `dropPosition > oldOrder` →
   `normalizedPosition = dropPosition - 1`. Если `oldOrder === normalizedPosition`
   → `[]` (no-op).

3. **Построение целевого списка**: взять задачи целевого дня (без перемещаемой),
   отсортированные по `order ?? 0`, вставить перемещаемую на `normalizedPosition`
   через `splice`.

4. **Diff**: сравнить `task.order !== index` для каждого элемента → updates.

5. **Уплотнение исходного дня** (cross-day only): аналогично — убрать задачу
   из исходного дня, перенумеровать, добавить updates.

6. **Формирование update перемещаемой**: если diff содержит её (order изменился)
   — добавить `dueDate`; иначе — добавить полный update `{ id, dueDate, order }`.

### Инвариант результата

После применения всех обновлений каждый затронутый день удовлетворяет
инварианту плотной нумерации `0..N-1`. Это гарантируется конструктивно
(renumber) и подтверждается property-based тестами.

## Защита инварианта `dueDate != null ⟹ order != null`

Инвариант защищён на двух уровнях. Route handler не содержит дополнительной
проверки, так как текущая простая логика partial-update не создаёт путей
нарушения при наличии первых двух слоёв.

### Слой 1: Zod-валидация (`api/src/schemas/task.schema.ts`)

`batchEditSchema.superRefine()` проверяет:

- Установка `dueDate` в non-null требует наличия `order` в том же update
- Сброс `dueDate` в null требует одновременного сброса `order` в null

Некорректный запрос отклоняется с 400 до обращения к БД.

### Слой 2: DB CHECK-констрейнт (`api/src/db/schema.ts`)

```sql
CONSTRAINT order_integrity_check CHECK(due_date IS NULL OR "order" IS NOT NULL)
```

Последний рубеж: даже при обходе валидации (прямой доступ к БД, баг в коде)
SQLite отвержет запись. Миграция: `drizzle/0002_lying_masque.sql`.

### Обработка аномалий в `computeReorder`

При наличии в дне задач с `dueDate != null && order == null` (legacy-данные,
возникшие до внедрения защиты) алгоритм автоматически восстанавливает инвариант
при перенумерации. После полного устранения legacy-данных это поведение станет
недостижимым путём штатных операций.

Компаратор сортировки унифицирован между `computeReorder` и геттером store
`taskIdsByDueDate`: оба используют `order ?? 0`.

## Optimistic update и откат (`reorderTask` в store)

```
1. updates = computeReorder(все задачи store, ...)
2. updates пуст → выход (запрос не отправляется)
3. snapshot всех затрагиваемых задач (both days)
4. немедленное применение updates к entities (UI обновляется синхронно)
5. PATCH /tasks с updates
6. успех → ответ сервера (Task[]) перезаписывает entities
   ошибка → восстановление всех задач из snapshot + request.status = 'error'
```

Snapshot включает все затронутые задачи обоих дней, а не только перемещаемую —
иначе откат оставил бы сдвинутые порядки соседей.

## Атомарность и гонки

- Бэкенд применяет весь batch в одной транзакции better-sqlite3
  (`api/src/routes/tasks.ts`, `db.transaction`). Любая ошибка → ROLLBACK,
  состояние «задача удалена из дня А, но не появилась в дне Б» невозможно.
- Оптимистичное обновление применяется синхронно до `await`, поэтому
  последовательные drop'ы вычисляются от уже обновлённого состояния —
  второй `computeReorder` видит результат первого даже если первый запрос
  ещё в полёте.
- HTTP/1.1 гарантирует порядок доставки запросов и ответов на одном
  соединении: сервер применяет batch'и в порядке отправки, последний ответ
  перезаписывает store консистентно. Очередь запросов не требуется
  (однопользовательское приложение).

## API-контракт

`PATCH /tasks`, тело: `BatchEditInput` (Zod: `batchEditSchema`, минимум одно
поле для обновления у каждой задачи, инвариант dueDate/order проверяется).
Ответ: `Task[]` — полные записи изменённых задач. Несуществующие id молча
пропускаются.

## Покрытие тестами

### Unit-тесты (`src/utils/__tests__/computeReorder.spec.ts`)

Юзкейсы по группам:

- **A1–A8** — между днями: пустой день, начало/середина/конец, день с одной
  задачей (перед/после), исходный день опустел/уплотнился;
- **B1–B7** — внутри дня: no-op (включая drop на своей карте), сдвиг
  вверх/вниз с нормализацией DOM-позиции, в начало, в конец (пустая область),
  единственная задача, swap двух;
- **C1–C5** — из TaskForm в день: пустой, начало, середина, конец; задача с
  `dueDate` обрабатывается как cross-day;
- **D1–D2** — сброс даты с уплотнением и без;
- **E** — несуществующая задача, позиция < 0, > N (cross-day и same-day),
  нецелочисленная позиция, повтор целевой позиции, unplanned → unplanned,
  соседи с `order = null`, задачи других дней не затрагиваются.

Property-based тесты:

- **Плотная перестановка**: для случайных конфигураций задач и перемещений
  результат всегда даёт плотную нумерацию `0..N-1` в каждом затронутом дне
  (200 итераций с детерминированным seed);
- **Cross-day инвариант**: отдельный прогон для перемещений между днями
  (100 итераций).

### Store-тесты (`src/stores/__tests__/task.spec.ts`)

Интеграция store: optimistic update всех затронутых задач, замена ответа
сервера, rollback при ошибке, no-op без запроса, последовательный reorder
от optimistic-состояния, cross-day move.

### Backend-тесты

- `api/src/schemas/__tests__/task.schema.spec.ts` — валидация инварианта
  dueDate/order (установка without order, сброс without order, корректные пары);
- `api/src/routes/__tests__/tasks.spec.ts` — интеграционные тесты CRUD +
  проверка CHECK-констрейнта на уровне БД (INSERT/UPDATE с нарушением → ошибка).
