# Переупорядочивание задач при drag-and-drop

Документ фиксирует соглашения, алгоритм и нюансы перемещения задач между днями
календаря и TaskForm. Реализация: `src/utils/tasks.ts` (`computeReorder`),
интеграция: `src/stores/task.ts` (`reorderTask`), тесты:
`src/utils/__tests__/computeReorder.spec.ts`, `src/stores/__tests__/task.spec.ts`.

## Соглашения (утверждены)

| Параметр | Решение |
| --- | --- |
| Тип `order` | Integer, плотная нумерация `0..N-1` внутри каждого дня |
| Инвариант | У задачи с `dueDate != null` всегда `order != null`; «дырок» в нумерации дня нет |
| Unplanned-задачи (`dueDate = null`) | Не имеют `order` (`null`). TaskForm сортирует их по `creationDate`, DnD внутри TaskForm — no-op |
| Исходный контейнер | После удаления задачи уплотняется (сдвиг −1 у всех, кто был ниже) |
| Позиция вставки | DOM-индекс `0..N` (см. «Контракт позиции») |
| Drop в пустую область | Вставка в конец списка |
| No-op | Запрос на сервер не отправляется |
| Batch drag | Не поддерживается (одна задача за операцию); намеренно не закладывался |
| Атомарность | Одна транзакция SQLite на бэкенде (`POST /tasks/edit`) |
| Frontend | Optimistic update с rollback на snapshot обоих затронутых дней |
| Валидация позиции | Невалидная позиция → пустой массив обновлений, запрос не отправляется |

Отклонённая альтернатива: дробный `order` (float, вставка как `(prev+next)/2`).
Причины: предел точности float64 (~50 вставок в одну точку) требует fallback
полной перенумерации — то есть integer-алгоритм пришлось бы писать всё равно;
недетерминированная сортировка при коллизиях; масштаб чисел (0.01–0.99 и т.п.)
не влияет на предел точности. Для синхронного однопользовательского
better-sqlite3 сдвиг десятков строк в транзакции стоит доли миллисекунды.

## Контракт позиции

`getDraggedTaskOrder(element, clientY)` возвращает DOM-индекс точки вставки
в целевом `[data-task-list]`:

- наведение на верхнюю половину карты с DOM-индексом `k` → `k`;
- наведение на нижнюю половину карты с DOM-индексом `k` → `k + 1`;
- drop в пустую область контейнера → `childElementCount` (вставка в конец).

Важный нюанс: при перемещении **внутри того же дня** перетаскиваемая карта
остаётся в DOM и входит в этот индекс. Поэтому `computeReorder` нормализует
позицию к семантике «удалить, затем вставить»:

```
newPosition = (sameDate && dropPosition > oldOrder) ? dropPosition - 1 : dropPosition
```

Пример: день `[X, Y, Z, W]`, X перетаскивается под Z (DOM-позиция 3).
Без нормализации X встался бы на индекс 3 (после W); с нормализацией —
`newPosition = 2`, итог `[Y, Z, X, W]`, что соответствует визуальному
индикатору (border-bottom у Z).

Для cross-day перемещений перетаскиваемой карты в целевом DOM нет, позиция
уже соответствует семантике «вставить в список без перемещаемой задачи».

Валидные диапазоны: cross-day — `0..M` (M = число задач в целевом дне);
same-day — `0..M-1` после нормализации. Выход за диапазон, нецелочисленная
или отрицательная позиция → `computeReorder` возвращает `[]` (запрос не
отправляется, карта визуально возвращается на место).

## Алгоритм `computeReorder(allTasks, movedTaskId, newDueDate, dropPosition)`

Возвращает минимальный набор `ReorderUpdate[]` — только фактически изменённые
задачи. Пустой массив = no-op или невалидные данные.

### 1. Сброс даты (день → TaskForm, `newDueDate = null`)

- задача была unplanned → `[]` (no-op);
- иначе: перемещаемой задаче `dueDate = null, order = null`; все задачи
  исходного дня с `order > oldOrder` получают `order - 1` (уплотнение).
  `dropPosition` игнорируется.

### 2. Перемещение внутри дня (`oldDueDate === newDueDate`)

Нормализовать позицию (см. выше). Если `newPosition === oldOrder` → `[]`.

Сдвигаются только задачи между старой и новой позицией:

- сдвиг вниз (`oldOrder < newPosition`): задачи с `oldOrder < order <= newPosition`
  получают `order - 1`;
- сдвиг вверх (`oldOrder > newPosition`): задачи с `newPosition <= order < oldOrder`
  получают `order + 1`;
- перемещаемая задача получает `order = newPosition`.

Задачи вне затронутого диапазона не меняются и в обновления не попадают.

### 3. Перемещение между днями (включая TaskForm → день)

- уплотнение исходного дня (если `oldDueDate != null`): задачи исходного дня
  с `order > oldOrder` получают `order - 1`;
- раздвижение целевого дня: задачи целевого дня с `order >= newPosition`
  получают `order + 1`;
- перемещаемая задача получает `dueDate = newDueDate, order = newPosition`.

Из TaskForm (`oldDueDate = null`) уплотнения исходного контейнера нет —
unplanned-задачи не имеют order.

### Инвариант результата

После применения всех обновлений каждый затронутый день удовлетворяет
инварианту плотной нумерации `0..N-1`. Задачи с `order = null` в дне
(аномалия данных) игнорируются алгоритмом и не учитываются при подсчёте
позиций; геттер `taskIdsByDueDate` трактует `null` как 0.

## Optimistic update и откат (`reorderTask` в store)

```
1. updates = computeReorder(все задачи store, ...)
2. updates пуст → выход (запрос не отправляется)
3. snapshot всех затрагиваемых задач (both days)
4. немедленное применение updates к entities (UI обновляется синхронно)
5. POST /tasks/edit с updates
6. успех → ответ сервера (Task[]) перезаписывает entities
   ошибка → восстановление всех задач из snapshot + request.status = 'error'
```

Snapshot включает все затронутые задачи обоих дней, а не только перемещаемую —
иначе откат оставил бы сдвинутые порядки соседей.

## Атомарность и гонки

- Бэкенд применяет весь batch в одной транзакции better-sqlite3
  (`api/src/routes/tasks.ts`, `db.transaction`). Любая ошибка → ROLLBACK,
  состояние «задача удалена из дня А, но не появилась в дне Б» невозможно.
- Оптимистичное обновление применяется синхронно до `await`, поэтому
  последовательные drop'ы вычисляются от уже обновлённого состояния —
  второй `computeReorder` видит результат первого даже если первый запрос
  ещё в полёте.
- HTTP/1.1 гарантирует порядок доставки запросов и ответов на одном
  соединении: сервер применяет batch'и в порядке отправки, последний ответ
  перезаписывает store консистентно. Очередь запросов не требуется
  (однопользовательское приложение).

## API-контракт

`POST /tasks/edit`, тело: `{ tasks: ReorderUpdate[] }` (Zod: `batchEditSchema`,
минимум одно поле для обновления у каждой задачи). Ответ: `Task[]` — полные
записи изменённых задач. Несуществующие id молча пропускаются (на клиенте
невозможны: `computeReorder` возвращает `[]` для неизвестной задачи).

Примечание: описание контракта в AGENTS.md (`PATCH /api/task/:id` с
`Task | Task[]`) устарело — фактический эндпойнт `POST /tasks/edit`.

## Покрытие тестами

`src/utils/__tests__/computeReorder.spec.ts` — юзкейсы по группам:

- **A1–A8** — между днями: пустой день, начало/середина/конец, день с одной
  задачей (перед/после), исходный день опустел/уплотнился;
- **B1–B7** — внутри дня: no-op (включая drop на своей карте), сдвиг
  вверх/вниз с нормализацией DOM-позиции, в начало, в конец (пустая область),
  единственная задача, swap двух;
- **C1–C5** — из TaskForm в день: пустой, начало, середина, конец; задача с
  `dueDate` обрабатывается как cross-day;
- **D1–D2** — сброс даты с уплотнением и без;
- **E** — несуществующая задача, позиция < 0, > N (cross-day и same-day),
  нецелочисленная позиция, повтор целевой позиции, unplanned → unplanned,
  соседи с `order = null`, задачи других дней не затрагиваются.

`src/stores/__tests__/task.spec.ts` — интеграция store: optimistic update
всех затронутых задач, замена ответа сервера, rollback при ошибке, no-op без
запроса, последовательный reorder от optimistic-состояния, cross-day move.
